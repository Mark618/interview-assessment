Design Decisions – AI Word Chain Game (n8n Implementation)

1. Architecture Design

1.1 Workflow-Based Architecture

The system is built entirely using n8n workflows, leveraging:

  • Chat Trigger as the entry point

  • Modular nodes (Switch, IF, Code, AI Agent) for logic control

  • Google Sheets for persistence

This approach was chosen for:

  • Rapid development

  • Low infrastructure overhead

  • Easy visualization of logic flow

1.2 Modular Design

The workflow is divided into logical components:

  • User Interaction Layer

    • Handles chat messages and responses

      • Managed via Chat nodes

  • Command Processing Layer

    • Parses input (SplitInput node)

    • Routes commands using Switch node

  • Game Logic Layer

    • Word validation (Code node + AI Agent)

    • Score calculation and round tracking

  • Persistence Layer

    • Google Sheets used for storing:

      • Game state (games_table)

      • Player stats (player_stats)

2. State Management Strategy

2.1 Session-Based State

  • Each game session is identified using sessionId from the chat trigger

  • Game progress is stored in Google Sheets using:

    • game_id

    • current_round

    • score

    • outcome (last word)

2.2 Persistence Design

Instead of in-memory storage, persistent storage ensures:

  • Game continuity across messages

  • Stateless workflow execution

  • Easier debugging and inspection

3. Command Handling

3.1 Input Parsing

  • Implemented using a custom Code node (SplitInput)

  • Extracts:

    • Command (start, stats, help, quit)

    • Difficulty level

    • Regex-based parsing ensures flexibility

3.2 Command Routing

  • Switch node routes requests into:

    • Start Game

    • Stats

    • Help

    • Quit

This separation keeps logic clean and maintainable.

4. Game Logic Design

4.1 Word Validation

Two-step validation approach:

  1. Rule-based validation (Code Node)

    • Ensures correct format (submit [word])

    • Checks first-letter rule against previous word

  2. AI-based validation (AI Agent)

    • Validates if word is real English word

    • Applies difficulty constraints

    • Calculates score

  3. This hybrid approach ensures:

    1. Deterministic rule enforcement

    2. Flexible and intelligent validation via AI

4.2 Difficulty Handling

Difficulty is enforced via AI prompt:

  • Easy: 4–6 letters

  • Medium: 6–8 letters

  • Hard: 8–12 letters + rare endings

This reduces complexity in code and leverages LLM flexibility.

4.3 Scoring System

Score is computed by AI Agent based on:

  • Base score: 10 points

  • Length bonus

  • Creativity bonus (rare letters)

The score is accumulated and updated in storage.

5. Data Storage Design

5.1 Choice of Google Sheets

Google Sheets was chosen because:

  • Easy integration with n8n

  • No setup required

  • Human-readable and easy to debug

5.2 Schema Design

Games Table

  • game_id

  • username

  • difficulty

  • current_round

  • score

  • outcome

  • timestamp

Player Stats Table

  • username

  • total_games

  • best_score

  • avg

  • difficulty

5.3 Trade-offs

  • Pros:

    • Simplicity

    • Fast setup

  • Cons:

    • Limited scalability

    • No strong consistency guarantees

6. Game Flow Design

6.1 Game Initialization

  • User enters name → extracted via AI

  • Game starts with start [difficulty]

  • New record created if none exists

6.2 Game Loop

  • User submits word

  • Validation pipeline:

    • Format check

    • Rule validation

    • AI validation

  • Score updated

  • Round incremented

6.3 Game Termination

  • Ends when:

    • 10 rounds completed

    • User quits

Final stats are saved into player_stats.

7. Error Handling Strategy

  • Invalid input handled early (Code node)

  • AI output validated using structured parser

  • Fallback responses:

    • Invalid format → prompt correction

    • Invalid word → explanation

This ensures robustness and better user experience.

8. AI Integration Design

8.1 Model Choice

  • Google Gemini used for:

    • Name extraction

    • Word validation

    • Scoring

8.2 Prompt Engineering

  • Clear system prompts define:

    • Rules

    • Difficulty constraints

    • Output format

8.3 Structured Output

  • JSON schema enforced using Output Parser

  • Ensures reliable downstream processing

9. Alternatives Considered

9.1 Database (PostgreSQL / SQLite)

  • More scalable and structured

  • Not chosen due to:

    • Increased setup complexity

    • Overkill for prototype

9.2 Fully Rule-Based Validation

  • More deterministic

  • Not chosen because:

    • Hard to validate real English words

    • Less flexible for scoring
